## Feature and review

The Fixed Stock field accepts one concentration or an explicit pair such as
`5, 500`. Two values enable the pair regardless of the automatic two-stock
checkbox. Both stocks remain present when either or both are unused. Inputs
must be positive, finite and distinct at the existing two-decimal stock-ID
precision. Maximum-stock and printed-volume constraints still apply; invalid
input or an infeasible plan preserves the last valid outputs.

Reviewed path: designer field -> shared FixedStock parsing -> OptionSpec ->
ExperimentModel optimization -> existing two-stock target evaluator/nearest
solver -> existing stock allocation, calibration, finalization and execution
resume. Controller dispatch, machine communication and firmware handlers are
unchanged. Review covered normalization, failure paths, allocation validation,
worker cancellation/stale publication, fingerprints, reusable plans, unused
stocks, serialization, editable copies and progress overrides. No actionable
feature finding was identified. This is the preparing agent's review, not a
separate human approval.

Existing designs remain readable. Pair designs persist the optional
`forced_stock_concs` constraint; older designers do not support that constraint.
No historical downgrade is qualified for this release. Machine-data schema,
execution-calibration version 4 and the existing execution-data capabilities
are retained, with no configuration/data migration.

## Discovery, recovery and limitations

Stable schema v1 explicitly declares only `v1.2.0-rc.6`, `v1.2.0` and
`v1.3.0-rc.1` as direct legacy sources. The exact rc.11 pointer, its legacy
cohorts and the v1.3.0 RC series stay unchanged. Tests execute immutable legacy
updaters for both stable discovery and that RC fallback, check unchanged local
configuration/calibration/bundle bytes, and exercise real bootstrap enrollment
and rejection before pointer publication.

`rollback_version` remains null. Even a release with matching execution-data
capability declarations is not an exactly qualified fixed-pair rollback target.
Preserve measurements, committed counts, progress and immutable revisions; use
protected current-version recovery or a qualified compatible offline bundle.
Direct legacy deployment retains the existing guarded migration, dependency,
firmware/recovery verification and attended first-machine canary requirements.

No new long-session Pi memory, historical replay or optimizer timing claim is
made. The accepted large-optimizer UI-pause limitation remains unchanged.
