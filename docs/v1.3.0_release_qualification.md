those clients. The new final manifest explicitly declares exactly:

- `v1.2.0-rc.6`;

at `v1.3.0-rc.11`; its series declaration, exact source cohorts, and bridge

retain their schema-v2 barrier for immutable older clients.

Thirteen new release cases execute each immutable updater's original bytes
against the actual proposed final metadata, testing both stable and RC channels.
They verify final stable selection or the existing rc.11 route and preservation
of complete synthetic configuration/calibration memory plus legacy bundle
remnants. Real bootstrap paths accept each declared cohort, reject missing,
undeclared, or wildcard authority before active-pointer/anchor publication,
and verify that the final release offers no automatic historical rollback.

An additional owned-clone campaign starts at actual `origin/stable` commit
`ea1030cab7e03caae66de6bb1161a91c5a851c36`, using its immutable v1.2.0 updater.
It fast-forwards to prepared commit `6ee3a41f`, preserves all 11 synthetic local
configuration/calibration files, and does not relaunch the app. The v1.3.0 tag
used by this campaign exists only in its disposable test origin, not in the

A separate protected rc.15-to-final campaign passes with unchanged hashes for

These are host-only campaigns using owned repositories and synthetic stores.

Real legacy rollout still requires the established operator-reviewed preserved

preflight, and an attended first-machine canary. Software qualification does
not establish an installed interpreter, firmware, or machine-specific physical
configuration. No live-machine migration or new hardware authority is granted.

## Rollback and recovery

The final `rollback_version` remains null. Actual historical tag inspection
confirms v1.2.0 and rc.11 lack the required execution-data declaration for
`execution_calibrations_v4` and `execution_volume_budget_v1`. Later RCs declare
these capabilities, but declarations alone do not qualify an exact rollback
campaign. No older application version is advertised as a fallback.

Preserve measurements, committed counts, progress, immutable revisions and
version-4 calibration history. Use protected current-version recovery or an
exactly qualified compatible offline bundle. The rc.8 released-firmware anchor
is a firmware recovery binding, not permission to downgrade the application or
rewrite experiment documents. Follow the machine-data update/rollback runbook;
do not manually edit pointers, anchors, receipts or firmware state.

## Stable ancestry and publication order

Current remote stable has a separate metadata-only commit that is not an
ancestor of rc.15. Publishing a tag based solely on rc.15 would fail the normal
fast-forward-only update from that stable checkout. The preparation branch
therefore joins `origin/stable` at `ea1030ca`. The only conflict was
`releases/latest.json`, resolved to the already validated final index. Its
entire resulting tracked tree equals f30379d5, so the full validation applies
without a runtime rerun. The actual immutable-updater campaign above verifies
the resulting history, not only a synthetic version sequence.

Before publication, review the exact final preparation commit and evidence.
Check protected remote refs again; if either branch moved, re-evaluate ancestry
and any payload difference. With explicit publication authority, integrate this
reviewed preparation into main without introducing payload changes, create the
new annotated v1.3.0 tag on the exact accepted metadata revision, run
`tools/validate_release_metadata.py --check-tags`, and push the tag before the
branches that advertise it. Advance stable only by a validated fast-forward;
never force it or retarget an existing release tag. PR #6 can follow the stable
promotion as development work, without a separate app-release bump.

`--check-tags` is intentionally pending until an actual v1.3.0 tag is authorized
and created. No release-aware installable update bundle is generated during
preparation. External source ZIP and Git review bundle files are tag-free review
artifacts, not deployment packages.
